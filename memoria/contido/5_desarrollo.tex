\chapter{Desarrollo}
\label{chap:desarrollo}

En este capítulo se describe el proceso seguido para construir la aplicación. La explicación se plantea como una evolución por versiones: primero se comprobó que la idea era viable, después se desarrolló el árbol de decisión y, a partir de las primeras pruebas, se fueron incorporando explicaciones, animaciones y formas más claras de elegir los datos de entrada.


\section{Prototipo: versión 0.1}

El primer objetivo consistió en comprobar que la herramienta elegida servía para crear una aplicación interactiva y publicarla como página web. Antes de invertir más tiempo en el desarrollo, era necesario verificar tres aspectos básicos: que Godot permitía crear una interfaz sencilla, que se podía representar una estructura con forma de árbol y que el resultado podía ejecutarse desde el navegador.

Por ese motivo, la primera versión del proyecto fue deliberadamente simple. Consistía en un menú inicial y en una escena donde el usuario podía crear pequeños elementos conectados entre sí. Al pulsar sobre uno de ellos aparecía una opción para añadir un nuevo elemento debajo, de manera que poco a poco se formaba una estructura parecida a un árbol. Esta prueba estaba todavía lejos de un árbol de decisión real. Su valor estaba en comprobar si la interacción principal de la aplicación tenía sentido.

Para iniciar este proceso, primero hizo falta entender cómo se organiza un proyecto en Godot. Esta base se explica en la Sección \ref{sec:herramientas_godot}.

\subsection{Exportación web con GitHub Pages}

Una vez que la prueba interactiva funcionaba dentro de Godot, el siguiente paso lógico fue llevarla al navegador. Esta comprobación era esencial, ya que la aplicación estaba pensada para ser consultada como una página web y también debía poder probarse fuera del editor de desarrollo.

La exportación se realizó correctamente con este proyecto inicial. El resultado se publicó mediante GitHub Pages, usando la configuración del propio repositorio para indicar qué carpeta debía servir como página web. Con esto se confirmó que el flujo completo era viable: desarrollar en Godot, exportar el proyecto y publicarlo en una dirección accesible desde el navegador.

Esta prueba temprana redujo el riesgo del proyecto. Si la exportación web hubiese dado problemas graves, habría sido necesario replantear la tecnología antes de avanzar con los algoritmos. Al funcionar desde el inicio, el desarrollo pudo continuar sobre una base más segura.


\section{Árbol de decisión: versión 0.2}

El proyecto dejó de ser un prototipo aislado cuando comenzó el desarrollo del primer algoritmo: el árbol de decisión. A partir de este punto, el reto pasó a consistir en conseguir que el árbol se construyese siguiendo las decisiones del algoritmo y que el usuario pudiese entender cada paso.


\subsection{Primera arquitectura del árbol}

El primer cambio fue separar la prueba visual inicial de una estructura preparada para crecer. El árbol tenía que convertirse en una vista capaz de representar tanto acciones del usuario como decisiones tomadas por el algoritmo.

Para ello se mantuvo el menú principal como entrada de la aplicación y se creó una vista específica para el árbol. Esta vista debía resolver un problema práctico desde el principio: un árbol puede crecer hacia abajo y hacia los lados con mucha rapidez. Si todo se colocaba en una pantalla fija, una parte del contenido quedaría fuera de la vista en cuanto apareciesen varios niveles. Por esta razón se introdujo una zona desplazable, de forma que el usuario pudiese moverse por el árbol cuando su tamaño aumentase.

También se revisó la forma de colocar los elementos. La versión inicial podía añadir hijos bajo un nodo y el resultado necesitaba más orden. Se adoptó una distribución sencilla: los hijos se colocaban por debajo de su padre y el padre quedaba centrado respecto a ellos. Esta decisión buscaba mantener una lectura clara y estable cada vez que el árbol cambiaba.

Otro aspecto importante fue separar visualmente los elementos del árbol y las líneas que los unen. Esta separación hizo que cada parte tuviese una responsabilidad clara: unos elementos representaban preguntas o resultados, y las líneas representaban el camino seguido entre ellos. Gracias a esto, más adelante fue más sencillo animar las ramas y mostrar sobre ellas el valor que conducía de un punto del árbol al siguiente.

En esta etapa se conservó también el modo manual. El objetivo principal era construir árboles de decisión, y el modo manual seguía siendo útil para probar la interfaz, comprobar el desplazamiento por la pantalla y detectar problemas de colocación sin depender todavía del algoritmo.

El siguiente avance fue preparar el modo automático. En este modo, el usuario dejaba de añadir ramas a mano y pasaba a controlar el avance del entrenamiento. La primera versión de esta interfaz era todavía muy simple, con botones en inglés, como se muestra en la Figura \ref{fig:dtree_view_start_next_english}. Esta pantalla introducía una idea que se mantuvo durante todo el desarrollo: el algoritmo avanzaría al ritmo marcado por el usuario.

Para conseguirlo, el algoritmo se organizó de forma incremental. La construcción completa se repartía en pasos pequeños: se guardaba el punto en el que se encontraba el proceso y se resolvía una parte cada vez que el usuario pulsaba el botón de avanzar. Esta decisión fue clave para el propósito educativo de la aplicación, porque permitía observar cómo se forma el árbol paso a paso.

La primera prueba de entrenamiento utilizó un conjunto de datos pequeño y controlado. Su objetivo era comprobar que el árbol se creaba correctamente, que las ramas aparecían donde debían y que la interfaz se actualizaba después de cada paso. En esta fase, lo más difícil fue coordinar tres niveles al mismo tiempo: el estado interno del algoritmo, la estructura del árbol y lo que el usuario veía en pantalla.


\subsection{Reorganización de la escena y primeros elementos explicativos}

Cuando el modo automático empezó a funcionar, se reorganizó la escena para simplificarla. Algunas piezas que habían sido útiles durante las pruebas iniciales dejaron de ser necesarias, así que se redujo la cantidad de elementos intermedios. Esta limpieza facilitó seguir avanzando sin arrastrar soluciones provisionales.

Uno de los problemas que apareció al reorganizar la vista fue el centrado del árbol. Al crecer, el árbol podía quedar desplazado hacia una esquina, lo que dificultaba seguir la construcción. Se ajustó entonces el comportamiento de la zona desplazable para que el contenido apareciese centrado y el usuario pudiese moverse por él de forma natural. Esta mejora mantenía intacto el algoritmo y afectaba mucho a la experiencia de uso.

La escena del árbol empezó a funcionar como un pequeño flujo guiado. Primero se mostraba un panel para escoger entre crear el árbol manualmente o dejar que lo construyese el algoritmo. Después, según la opción elegida, aparecían los controles correspondientes. En la Figura \ref{fig:menu_manualmente_algoritmicamente} se muestra este panel inicial.

Esta distinción visual ayudaba a leer el árbol sin depender tanto del texto: algunas partes indicaban que todavía había una pregunta que responder, y otras indicaban que se había llegado a una conclusión.

La ventana nació para cubrir esa carencia: debía acompañar a la construcción del árbol con una explicación escrita del paso actual.

Su primera versión contenía un mensaje inicial que invitaba al usuario a comenzar el entrenamiento. Más adelante se convirtió en un componente propio, separado de la vista principal, porque iba a necesitar textos distintos según el caso y debía poder actualizarse cada vez que avanzase el algoritmo. Los primeros textos de la ventana explicaban tres situaciones frecuentes. La primera era la creación de un nodo de decisión, cuando el algoritmo todavía tenía que escoger por qué característica dividir los datos. La segunda era la creación de una hoja porque todos los ejemplos que llegaban a ese punto tenían la misma respuesta. La tercera era la creación de una hoja por mayoría, usada cuando ya no había más preguntas útiles y se debía escoger la respuesta más frecuente.

Durante estas pruebas se detectó que el texto necesitaba una preparación previa. Algunas listas aparecían con un formato propio de programación y poco adecuado para la lectura. Por ello se preparó la información antes de enseñarla, transformándola en frases más naturales. Esta fue una decisión importante para el tono de la aplicación: la ventana debía parecer una explicación dirigida al usuario.

También se empezó a mostrar el criterio usado para escoger la siguiente división. En esta primera fase aparecía como texto, con una línea por cada opción evaluada. Era una solución básica y permitió conectar el cálculo del algoritmo con una explicación visible dentro de la interfaz. A partir de aquí, la aplicación construía el árbol y empezaba a justificarlo.


\subsection{Animación de la construcción del árbol}

Con la construcción paso a paso funcionando, apareció un nuevo problema: los cambios eran demasiado bruscos. Cada pulsación podía crear un nodo, mover partes del árbol y dibujar nuevas ramas. El resultado era correcto. En algunos pasos, el usuario podía perder de vista qué elemento acababa de aparecer.

Para mejorar esta lectura se añadieron animaciones. Primero se animaron las ramas, de manera que cada conexión parecía crecer desde el punto anterior hasta el nuevo. Después se animó la aparición de los nodos, que dejaban de mostrarse de golpe y pasaban a aparecer de forma gradual. Estas animaciones dirigían la atención hacia el cambio producido en cada paso.

Al introducir animaciones fue necesario revisar cómo se actualizaban las conexiones. En las primeras versiones, al modificar el árbol se redibujaban todas las ramas. Esto hacía que, cada vez que aparecía una conexión nueva, también se reiniciasen las que ya existían. Se cambió este comportamiento para conservar las ramas anteriores y animar solo las recién creadas. Gracias a ello, el avance resultaba más claro y menos repetitivo.

Después se incorporó una idea pensada específicamente para explicar mejor el algoritmo: los nodos pendientes. Cuando el árbol decide dividir los datos por una característica, ya se sabe qué caminos van a aparecer y todavía falta conocer qué habrá al final de cada uno. Para representar ese estado intermedio, la aplicación empezó a mostrar nodos temporales con un aspecto distinto.

Estos nodos pendientes indicaban que el algoritmo ya había abierto una rama y que aún quedaba por resolver su contenido. Más adelante, cuando esa parte del árbol se procesaba, el nodo temporal se transformaba en una decisión real o en una clasificación final. Esta transición también se animó para que el usuario percibiese el cambio y entendiese que se estaba completando una parte que antes solo estaba prevista.

Otra prueba temprana consistió en mostrar un valor numérico al pasar el cursor por ciertos nodos. La intención era permitir consultar información sobre la decisión tomada sin llenar todo el árbol de números. La idea funcionaba de forma limitada: un número aislado dice poco si no se explica qué significa. Por esa razón, más adelante esa información se trasladó hacia la ventana informativa, donde podía acompañarse de una explicación más completa.


\subsection{Gráficas y casos explicativos en la ventana}

La ventana informativa evolucionó después de los primeros textos. A medida que el árbol crecía y los pasos se volvían más ricos, una única explicación en texto plano resultaba insuficiente. El objetivo pasó a ser combinar texto y apoyo visual para que la decisión del algoritmo fuese más fácil de seguir.

El cambio principal fue introducir una gráfica de barras. La ventana pasó de una lista de valores a una comparación visual entre las opciones que el algoritmo estaba evaluando. Así era más sencillo ver cuál destacaba y por qué se escogía una división determinada.

Para integrar esta gráfica, la ventana pasó a tener una estructura desplazable. Esto era necesario porque algunas explicaciones ocupaban más espacio que otras. El usuario podía leer la primera parte del texto, observar la gráfica y continuar después con la explicación del resultado. De esta forma, la gráfica quedaba dentro del relato del paso actual.

Este cambio obligó también a preparar mejor la información que recibía la ventana. Los valores utilizados para la gráfica debían conservarse como datos numéricos, sin transformarlos desde el inicio en frases ya formateadas. Esta separación permitió que la misma información sirviese para explicar el paso con texto y para construir la representación visual.

En esta etapa se añadió además un caso explicativo para los empates. Durante las pruebas apareció una situación en la que varias opciones podían ser igual de buenas. Si la aplicación escogía una sin explicar nada, la decisión podía parecer arbitraria. Por eso se incorporó un texto específico que indicaba que había varias alternativas equivalentes y que el algoritmo continuaba con una de ellas.

También se revisaron los textos de las hojas. Las primeras frases estaban escritas pensando en ejemplos muy pequeños, donde a veces solo llegaba un dato a cada resultado final. Al probar conjuntos más variados, esa redacción dejó de ser válida. Se sustituyó por una explicación más general, capaz de describir tanto un único ejemplo como varios ejemplos que terminan en la misma clasificación.

Este proceso se repitió varias veces durante el desarrollo: al probar nuevos datos aparecían casos que la explicación inicial no cubría bien. Esos casos se fueron incorporando al discurso de la aplicación para que el usuario no tuviese que interpretar silencios o comportamientos inesperados.


\subsection{Primer panel de selección de datos}

Hasta este momento, los datos usados para entrenar el árbol estaban fijados dentro del propio proyecto. Esto era cómodo para las primeras pruebas, porque permitía centrarse en el funcionamiento del algoritmo y de la interfaz. Con el tiempo, esta comodidad empezó a limitar la aplicación: el usuario necesitaba poder escoger con qué ejemplo trabajar.

El siguiente paso fue separar la elección de los datos del entrenamiento. Primero se probó un segundo conjunto preparado manualmente, con casos diseñados para forzar ramas más profundas y situaciones menos evidentes. Esta prueba ayudó a comprobar que el árbol también funcionaba con ejemplos distintos del primero y que los textos seguían teniendo sentido cuando los datos cambiaban.

A partir de ahí se creó un panel de selección. Su papel era guiar al usuario antes de empezar el entrenamiento: primero se elegía una fuente de datos y después se iniciaba la construcción del árbol. La primera opción permitía usar el conjunto de ejemplo incluido en la aplicación. La segunda opción abría la puerta a cargar un archivo CSV.

La carga de archivos se introdujo de forma progresiva. En una primera versión, el panel ya mostraba la opción de CSV y todavía estaba incompleta. Después se añadió la lectura del archivo y la comprobación de que la selección fuese válida antes de permitir entrenar. También se añadieron mensajes de éxito o error para que el usuario supiese si podía continuar.

Con este panel, el flujo del modo algorítmico cambió de manera importante. Antes, el usuario pulsaba directamente el botón de comenzar. Después de esta mejora, primero escogía los datos, luego confirmaba la selección y finalmente avanzaba por la construcción del árbol. Esta separación hacía el proceso más comprensible, porque dejaba claro que el entrenamiento depende de los datos elegidos.

La versión inicial del panel todavía era provisional. Quedaban detalles por ajustar, como mejorar la detección de la respuesta esperada en archivos externos y pulir la transición entre la selección de datos, el árbol y la ventana informativa. Con esas limitaciones pendientes, el cambio marcó un avance importante: el árbol dejó de estar ligado a un único ejemplo y empezó a comportarse como una herramienta más flexible.


\subsection{Carga de CSV y navegación por pasos}

El primer ajuste tras introducir el panel de datasets fue hacer que la carga de CSV fuese usable para entrenar. Se añadió una lista de nombres habituales para la columna objetivo, ``class'', ``Class'', ``y'', ``Y'', ``label'' y ``Label''. Al leer un CSV, el panel convertía las cabeceras a ``Array[String]'' con ``safe\_get\_array\_of\_strings'' y, una vez cargadas las filas, eliminaba de la lista de atributos la primera cabecera que coincidiese con uno de esos nombres. Así el array ``attrs\_info'' dejaba de incluir la etiqueta, y el controlador podía detectar la columna objetivo como la diferencia entre las claves del dato y los atributos.

También se corrigió la lectura de filas. En Godot, ``eof\_reached'' se activa después de intentar leer más allá del final, por lo que el bucle inicial podía resultar incómodo de razonar. La versión corregida usaba un ``while true'', leía una fila con ``get\_csv\_line'', comprobaba después si se había alcanzado el final y salía del bucle en ese caso. Las filas vacías se ignoraban y cada fila válida se convertía en un diccionario. Este parseo seguía siendo sencillo y ya era suficiente para cargar datasets categóricos externos con una cabecera y varias filas.

La vista del árbol ajustó su visibilidad al nuevo flujo. Al escoger el modo algorítmico se mostraba el panel de selección de dataset, mientras que el árbol y la ventana quedaban ocultos. Después de recibir ``SignalsObserver.dataset\_selected'', se mostraban el ``ScrollContainer'' y la ventana. Con ello el usuario no veía un árbol vacío ni una ventana de explicación antes de haber elegido los datos. El texto inicial de la ventana se cambió a ``Presiona el botón \"Siguiente\"'', porque el entrenamiento ya empezaba al seleccionar el dataset y no al pulsar un botón de entrenamiento dentro del panel algorítmico.

En ese mismo momento empezó a prepararse la navegación hacia atrás. Se añadió la señal ``previous\_step'' al controlador, se conectó con el algoritmo y se creó un método ``previous\_step'' en ``AlgorithmDTree''. La primera versión solo movía el último contexto de ``called\_stack'' de vuelta a ``call\_stack'' y llamaba a ``\_unbuild\_node\_step'', que todavía estaba vacío. Aunque no deshacía nada, este cambio ya introducía las estructuras necesarias: una pila de pasos pendientes, ``call\_stack'', y otra de pasos ejecutados, ``called\_stack''.

Después se añadió el botón ``Paso previo'' al panel del algoritmo. La escena ``panel\_algorithm\_dtree.tscn'' incorporó ``PrevButton'', y el controlador guardó una referencia ``previous\_step\_button'', conectó su pulsación con ``\_on\_previous\_step\_button\_pressed'' y lo hizo visible al comenzar el entrenamiento. Desde la interfaz, el modo de construcción del árbol dejaba de ser estrictamente lineal. El usuario podía avanzar con ``Siguiente paso'' y retroceder con ``Paso previo'', una característica importante para una herramienta didáctica, porque permite revisar el punto exacto en el que aparece una rama o se decide una hoja.

La implementación real del retroceso se hizo en ``\_unbuild\_node\_step''. El algoritmo comprobaba primero que existiese una referencia válida al árbol y resolvía qué nodo visual correspondía al contexto que se quería deshacer. Para ello se añadió ``\_resolve\_context\_node\_id''. Este método intentaba usar ``context[\"node\_id\"]'' si ya estaba disponible. Si no lo estaba, buscaba el nodo raíz cuando el padre era ``-1'', o recorría los hijos del padre comparando ``branch\_value''. Esta segunda vía era necesaria porque algunos contextos se asociaban a placeholders creados antes de que el nodo se resolviese por completo.

Antes de borrar un nodo, el algoritmo determinaba si el contexto correspondía a un nodo interno con ``\_is\_internal\_context''. Para ello reutilizaba las mismas condiciones de construcción: si todas las etiquetas eran iguales, el contexto era una hoja; si no quedaban atributos, también era una hoja; en otro caso se trataba como un nodo interno. Cuando se deshacía un nodo interno, primero se eliminaban de ``call\_stack'' los contextos de sus hijos mediante ``\_remove\_child\_contexts\_for\_parent'', y después se eliminaban visualmente sus hijos con ``\_remove\_visual\_children\_for\_node''. Así se evitaba dejar en la pila tareas que dependían de un nodo que acababa de desaparecer.

La forma de deshacer dependía del origen del nodo. Si el contexto correspondía a la raíz, se eliminaba todo el subárbol y se ponía ``root\_id'' a ``null''. Si el nodo procedía de un placeholder, se restauraba como pendiente en lugar de borrarlo. Esto se hizo con ``restore\_node\_as\_pending'', que limpiaba ``attribute'', ``label'' e ``information\_variable\_value'', ponía ``is\_leaf'' a ``false'', ``is\_pending'' a ``true'' y llamaba a ``apply\_theme\_animated'' con el tema de pendiente y el texto ``...''. Si el nodo no procedía de un placeholder, se eliminaba con ``remove\_subtree\_and\_self''.

Para soportar ese borrado, ``DTreeLogical'' incorporó ``remove\_subtree\_and\_self''. El método comprobaba que el nodo existiese, duplicaba su lista de hijos, eliminaba cada subárbol de forma recursiva, retiraba el identificador del nodo en el padre, borraba la entrada de ``nodes\_dict'', actualizaba ``root\_id'' si era necesario y liberaba la instancia visual. Esta función era parecida al borrado del modo manual y quedó dentro del propio árbol para que el algoritmo pudiera usarla al deshacer pasos.

Al probar el retroceso apareció un problema al volver al paso cero: si el árbol quedaba vacío, el reposicionamiento no redibujaba las conexiones. La corrección consistió en hacer que ``relayout\_tree'' comprobaba si ``root\_id'' era ``null'' o si ``nodes\_dict'' estaba vacío. En ese caso llamaba igualmente a ``\_redraw\_edges'' y terminaba. Así el contenedor de conexiones podía eliminar las ramas que ya no existían. El controlador también reactivaba el botón de siguiente al pulsar ``Paso previo'', porque deshacer un paso debe permitir avanzar de nuevo.


\subsection{Primera evaluación visual del árbol}

El último avance de este tramo inicial fue una primera versión del modo de evaluación. Hasta entonces, la aplicación había mostrado cómo se construía el árbol; el uso de ese árbol para clasificar datos nuevos quedaba pendiente. La evaluación se introdujo con un enfoque visual: un dato de prueba se representaría como un objeto que cae por el árbol siguiendo las ramas marcadas por sus atributos.

El panel algorítmico incorporó dos botones nuevos: ``Evaluar'' y ``Dropear dato''. Durante el entrenamiento, ``Evaluar'' permanecía deshabilitado. Cuando el algoritmo emitía ``algorithm\_completed'', el controlador deshabilitaba ``Siguiente paso'' y habilitaba ``Evaluar''. Al pulsarlo, se ocultaban los botones de construcción y se volvía a mostrar el panel de selección de dataset. Esta reutilización del panel permitía escoger datos para probar el árbol después de haberlo entrenado.

El controlador empezó a distinguir entre dos fases mediante ``has\_train\_started''. La primera vez que recibía ``dataset\_selected'', guardaba los datos, configuraba el algoritmo e iniciaba el entrenamiento. Las siguientes veces interpretaba la selección como datos de evaluación, hacía visible ``Dropear dato'' y emitía ``SignalsObserver.start\_evaluation''. Esta solución era provisional y permitía reutilizar la misma señal global para entrenamiento y evaluación sin crear todavía una interfaz separada para cada fase.

Para representar cada muestra se creó ``EvalData''. Era una escena pequeña basada en ``Node2D'', con un ``ColorRect'' como forma visual y una variable ``data\_dict'' donde se guardaba el diccionario de atributos de la muestra. La función estática ``newone'' instanciaba la escena, asignaba el diccionario y devolvía el objeto listo para colocarse en la vista.

La lógica del recorrido quedó en ``EvalDataContainer''. Esta escena recibía el árbol entrenado y una lista de ``EvalData''. Al crearse, copiaba la información relevante de cada nodo del árbol a un diccionario ``nodes'': posición, profundidad, atributo, etiqueta, valor de rama y padre. Esta copia era útil porque el dato evaluado necesitaba recorrer la estructura aunque el algoritmo original ya hubiese terminado. El contenedor se conectaba a ``SignalsObserver.drop\_data'', de modo que cada pulsación en ``Dropear dato'' ejecutaba ``\_drop\_one\_data''.

El método ``\_drop\_one\_data'' tomaba la primera muestra pendiente, la añadía como hija del contenedor y buscaba la raíz identificando el nodo con profundidad cero. Después entraba en un bucle. En cada iteración movía el objeto ``EvalData'' hasta la posición del nodo actual con un ``Tween'' de 0.35 segundos y esperaba a que terminase. Si el nodo actual tenía etiqueta, el recorrido terminaba, porque se había llegado a una hoja. Si era un nodo interno, obtenía el atributo de división, buscaba en ``data\_dict'' el valor de ese atributo y localizaba entre los nodos copiados un hijo cuyo ``parent\_id'' coincidiese con el nodo actual y cuyo ``branch'' coincidiese con el valor de la muestra. Ese hijo pasaba a ser el siguiente nodo.

El algoritmo se conectó a esta fase mediante ``SignalsObserver.start\_evaluation''. En ``\_evaluate\_dtree'', convertía cada diccionario del dataset de evaluación en un ``EvalData'' y añadía a la escena actual un ``EvalDataContainer'' creado con el árbol y la lista de muestras. Las señales globales se ampliaron con ``start\_evaluation'', ``drop\_data'' y ``all\_data\_droped''. La última se emitía cuando ya no quedaban muestras por soltar.

Esta primera evaluación era todavía básica. Los datos se dibujaban como rectángulos simples, el contenedor se añadía directamente a la escena actual y el recorrido completo de una muestra se hacía de una vez hasta la hoja. Las mejoras posteriores, como el movimiento nivel a nivel, el apilado bajo hojas, el color por clase y la explicación de cada decisión en la ventana, pertenecen a una etapa posterior del desarrollo. Aun así, este commit dejó establecida la idea central del modo de evaluación: ver físicamente cómo una muestra atraviesa las decisiones del árbol hasta llegar a una clasificación.

Con este conjunto de cambios quedó completada la primera versión significativa del árbol de decisión. El proyecto pasó de dibujar nodos conectados a construir un árbol ID3 paso a paso, mostrar estados pendientes, animar la aparición de ramas y nodos, explicar la selección de atributos con texto y gráficos, cargar datasets sencillos y ejecutar una primera evaluación visual. A partir de aquí el desarrollo del árbol continuó con mejoras de interfaz, persistencia, adaptación a móvil y explicaciones más completas, que se tratarán en apartados posteriores para no mezclar esta primera fase con las revisiones finales.
