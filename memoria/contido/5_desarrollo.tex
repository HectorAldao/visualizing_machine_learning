\chapter{Desarrollo}
\label{chap:desarrollo}

En este capítulo se describe el proceso seguido para construir la aplicación.
La explicación se plantea como una evolución por versiones.
Comienza por comprobar que la idea es viable.
Después se desarrolla el árbol de decisión, desde sus inicios hasta el resultado funcional con todas las características que se buscaban.
Continúa con el desarrollo de la red neuronal, pasando por todas sus fases de creación y mejora.
Y termina con el pulido final de la interfaz y retoques a todas las características con las que cuenta el resultado final.

\section{Prototipo: versión 0.1}

El primer objetivo consiste en comprobar que la herramienta elegida sirve para crear una aplicación interactiva y publicarla como página web.
Antes de invertir más tiempo en el desarrollo, es necesario verificar tres aspectos básicos: que Godot permite crear una interfaz sencilla, que se puede representar una estructura con forma de árbol y que el resultado puede ejecutarse desde el navegador.

Por ese motivo, la primera versión del proyecto es deliberadamente simple.
Consiste en un menú inicial y en una escena donde el usuario puede crear pequeños elementos conectados entre sí.
Al pulsar sobre uno de ellos aparece una opción para añadir un nuevo elemento debajo, de manera que poco a poco se forma una estructura parecida a un árbol.

Su valor está en comprobar si la interacción principal de la aplicación tiene sentido.

En ese momento tiene un único botón, ya que su papel es servir como punto de entrada hacia la prueba del árbol.
Incluir este menú desde el principio ayuda a pensar la aplicación como un conjunto de módulos y facilita su ampliación posterior.

Esta primera prueba tiene una finalidad muy concreta: validar la interacción.
Lo importante es comprobar que el usuario puede construir una jerarquía visual, que las conexiones se actualizan y que la pantalla sigue siendo manejable al crecer el número de elementos.

\subsection{Exportación web con GitHub Pages}

Una vez que la prueba interactiva funciona dentro de Godot, el siguiente paso lógico es llevarla al navegador.
Esta comprobación es esencial, ya que la aplicación está pensada para ser consultada como una página web y también debe poder probarse fuera del editor de desarrollo.

La exportación se realiza correctamente con este proyecto inicial.
El resultado se publica mediante GitHub Pages, usando la configuración del propio repositorio para indicar qué carpeta debe servir como página web.
Con esto se confirma que el flujo completo es viable: desarrollar en Godot, exportar el proyecto y publicarlo en una dirección accesible desde el navegador.

Esta prueba temprana reduce el riesgo del proyecto.
Si la exportación web da problemas graves, hace falta replantear la tecnología antes de avanzar con los algoritmos.
Al funcionar desde el inicio, el desarrollo puede continuar sobre una base más segura.

\section{Árbol de decisión: versión 0.2}

El proyecto deja de ser un prototipo aislado cuando comienza el desarrollo del primer algoritmo: el árbol de decisión.
A partir de este punto, el reto pasa a consistir en conseguir que el árbol se construya siguiendo las decisiones del algoritmo y que el usuario pueda entender cada paso.


\subsection{Primera arquitectura del árbol}

El primer cambio consiste en crear una nueva escena, dejando de lado la prueba visual inicial.
Esta vista debe resolver un problema que se había dejado de lado para la prueba inicial: un árbol puede crecer hacia abajo y hacia los lados indefinidamente y con mucha rapidez.
Si todo se coloca en una pantalla fija, una parte del contenido puede quedar fuera de la vista en cuanto aparecen varios niveles.
Por esta razón se introduce por medio de un nodo especializado de Godot una zona desplazable, de forma que el usuario pueda mover la posición el árbol en pantalla cuando su tamaño exceda los límites de la misma.

También hace falta revisar la forma en la que se distribuyen los nodos.
La versión inicial puede añadir hijos bajo un nodo pero por cómo se distribuían los nodos en pantalla los nodos padre podían quedar mal distribuidos con respecto a los hijos.
Para solucionar este inconveniente se adapató el código para que generara una distribución más clara a la vista: los hijos se colocan por debajo de su padre y el padre queda centrado respecto a ellos.
Esta decisión busca mantener una lectura clara y estable cada vez que el árbol cambia.

Otro aspecto importante de cara al cómo iba a avanzar el proyecto es separar a nivel lógico los nodos del árbol y las conexiones que los unen.
Esto hace que cada parte tenga una responsabilidad clara: unos elementos representan preguntas o resultados, y las líneas representan el camino seguido entre ellos.
Gracias a esto, más adelante se hizo más sencillo tanto animar las ramas como mostrar sobre ellas el valor que conduce de un punto del árbol al siguiente.

Con estas cuestiones cerradas, el siguiente avance es preparar el modo automático.
En este modo, el usuario deja de añadir ramas a mano y pasa a controlar el avance del entrenamiento.
La primera versión de esta interfaz es todavía muy simple, con botones con texto en inglés por convencionalismos del gremio, como se muestra en la Figura \ref{fig:dtree_view_start_next_english}.
Esta pantalla introduce una idea importante que se mantiene durante todo el desarrollo: el algoritmo avanza al ritmo marcado por el usuario.
Y para conseguirlo, el algoritmo se organiza de forma incremental.
La construcción completa se reparte en pasos pequeños: se guarda el punto en el que se encuentra el proceso y se resuelve una parte cada vez que el usuario pulsa el botón de avanzar.
Esta decisión es clave para el propósito educativo de la aplicación, porque permite observar cómo se forma el árbol pudiendo atender a los pásos que este mismo ejecuta.

La primera prueba de entrenamiento utiliza un conjunto de datos pequeño y controlado.

En esta fase, lo más difícil es coordinar tres niveles al mismo tiempo: el estado interno del algoritmo, la estructura del árbol y lo que el usuario ve en pantalla.
La estructura del árbol y su representación ya eran un problema resulento en la primera iteración.
Sin embargo, el reto añadido en este punto fue la sincronización de estas partes con el recién creado algoritmo.
Para afrontar las dificultades de este sistema, el algoritmo y el árbol son dos entidades distintas.
La primera le dicta a la segunda cómo modificarse en base a los resultados que dicten los cálculos.


\subsection{Reorganización de la escena y primeros elementos explicativos}

Cuando el modo automático empieza a funcionar, se reorganiza la escena para simplificarla.
Algunas piezas que resultan útiles durante las pruebas iniciales dejan de ser necesarias, así que se reduce la cantidad de elementos intermedios.
Esta limpieza facilita seguir avanzando sin arrastrar soluciones provisionales.

Uno de los problemas que aparece al reorganizar la vista es el centrado del árbol.
Al crecer, el árbol puede quedar desplazado hacia una esquina, lo que dificulta seguir la construcción.
Se ajusta entonces el comportamiento de la zona desplazable para que el contenido aparezca centrado y el usuario pueda moverse por él de forma natural.
Esta mejora mantiene intacto el algoritmo y afecta mucho a la experiencia de uso.

La escena del árbol empieza a funcionar como un pequeño flujo guiado.
Primero se muestra un panel para escoger entre crear el árbol manualmente o dejar que lo construya el algoritmo.
Después, según la opción elegida, aparecen los controles correspondientes.
En la Figura \ref{fig:menu_manualmente_algoritmicamente} se muestra este panel inicial.

Los puntos que representan una decisión y los puntos que representan una clasificación final pasan a tener estilos diferentes.
Esta distinción visual ayuda a leer el árbol sin depender tanto del texto: algunas partes indican que todavía hay una pregunta que responder, y otras indican que se llega a una conclusión.

Los botones iniciales pasan a llamarse ``Empezar entrenamiento'' y ``Siguiente paso''.

El siguiente paso natural es añadir una ventana informativa.
Hasta ese momento, el árbol muestra qué se está creando y apenas explica por qué se toma cada decisión.
La ventana nace para cubrir esa carencia: debe acompañar a la construcción del árbol con una explicación escrita del paso actual.

Su primera versión contiene un mensaje inicial que invita al usuario a comenzar el entrenamiento.
Más adelante se convierte en un componente propio, separado de la vista principal, porque va a necesitar textos distintos según el caso y debe poder actualizarse cada vez que avance el algoritmo.

Los primeros textos de la ventana explican tres situaciones frecuentes.
La primera es la creación de un nodo de decisión, cuando el algoritmo todavía tiene que escoger por qué característica dividir los datos.
La segunda es la creación de una hoja porque todos los ejemplos que llegan a ese punto tienen la misma respuesta.
La tercera es la creación de una hoja por mayoría, usada cuando ya no hay más preguntas útiles y se debe escoger la respuesta más frecuente.

Durante estas pruebas se detecta que el texto necesita una preparación previa.
Algunas listas aparecen con un formato propio de programación y poco adecuado para la lectura.
Por ello se prepara la información antes de enseñarla, transformándola en frases más naturales.
Esta es una decisión importante para el tono de la aplicación: la ventana debe parecer una explicación dirigida al usuario.

También se empieza a mostrar el criterio usado para escoger la siguiente división.
En esta primera fase aparece como texto, con una línea por cada opción evaluada.
Es una solución básica y permite conectar el cálculo del algoritmo con una explicación visible dentro de la interfaz.
A partir de aquí, la aplicación construye el árbol y empieza a justificarlo.


\subsection{Animación de la construcción del árbol}

Con la construcción paso a paso funcionando, aparece un nuevo problema: los cambios son demasiado bruscos.
Cada pulsación puede crear un nodo, mover partes del árbol y dibujar nuevas ramas.
El resultado es correcto.
En algunos pasos, el usuario puede perder de vista qué elemento acaba de aparecer.

Para mejorar esta lectura se añaden animaciones.
Primero se animan las ramas, de manera que cada conexión parece crecer desde el punto anterior hasta el nuevo.
Después se anima la aparición de los nodos, que dejan de mostrarse de golpe y pasan a aparecer de forma gradual.
Estas animaciones dirigen la atención hacia el cambio producido en cada paso.

Al introducir animaciones es necesario revisar cómo se actualizan las conexiones.
En las primeras versiones, al modificar el árbol se redibujan todas las ramas.
Esto hace que, cada vez que aparece una conexión nueva, también se reinicien las que ya existen.
Se cambia este comportamiento para conservar las ramas anteriores y animar solo las recién creadas.
Gracias a ello, el avance resulta más claro y menos repetitivo.

Después se incorpora una idea pensada específicamente para explicar mejor el algoritmo: los nodos pendientes.
Cuando el árbol decide dividir los datos por una característica, ya se sabe qué caminos van a aparecer y todavía falta conocer qué hay al final de cada uno.
Para representar ese estado intermedio, la aplicación empieza a mostrar nodos temporales con un aspecto distinto.

Estos nodos pendientes indican que el algoritmo ya tiene una rama abierta y que aún queda por resolver su contenido.
Más adelante, cuando esa parte del árbol se procesa, el nodo temporal se transforma en una decisión real o en una clasificación final.
Esta transición también se anima para que el usuario perciba el cambio y entienda que se está completando una parte que antes solo queda prevista.
En la Figura \ref{fig:dtree_nodos_pendientes} se puede ver el aspecto estos nodos pendientes.

Otra prueba temprana consiste en mostrar un valor numérico al pasar el cursor por ciertos nodos.
La intención es permitir consultar información sobre la decisión tomada sin llenar todo el árbol de números.
La idea funciona de forma limitada: un número aislado dice poco si no se explica qué significa.
Por esa razón, más adelante esa información se traslada hacia la ventana informativa, donde puede acompañarse de una explicación más completa.


\subsection{Gráficas y casos explicativos en la ventana}

La ventana informativa evoluciona después de los primeros textos.
A medida que el árbol crece y los pasos se vuelven más ricos, una única explicación en texto plano resulta insuficiente.
El objetivo pasa a ser combinar texto y apoyo visual para que la decisión del algoritmo sea más fácil de seguir.

El cambio principal es introducir una gráfica de barras como la que se aprecia en la Figura \ref{fig:dtree_grafica_entropia}.
La ventana pasa de una lista de valores a una comparación visual entre las opciones que el algoritmo está evaluando.
Así es más sencillo ver cuál destaca y por qué se escoge una división determinada.

\begin{figure}[hp!]
  \centering
  \includegraphics[width=0.85\textwidth]{imaxes/dtree_grafica_entropia.png}
  \caption{Ventana informativa en la que se dibuja la gráfica de la entropía de cada atributo.}
  \label{fig:dtree_grafica_entropia}
\end{figure}

Para integrar esta gráfica, la ventana pasa a tener una estructura desplazable.
Esto es necesario porque algunas explicaciones ocupan más espacio que otras.
El usuario puede leer la primera parte del texto, observar la gráfica y continuar después con la explicación del resultado.
De esta forma, la gráfica queda dentro del relato del paso actual.

Este cambio obliga también a preparar mejor la información que recibe la ventana.
Los valores utilizados para la gráfica deben conservarse como datos numéricos, sin transformarlos desde el inicio en frases ya formateadas.
Esta separación permite que la misma información sirva para explicar el paso con texto y para construir la representación visual.

En esta etapa se añade además un caso explicativo para los empates.
Durante las pruebas aparece una situación en la que varias opciones pueden ser igual de buenas.
Si la aplicación escoge una sin explicar nada, la decisión puede parecer arbitraria.
Por eso se incorpora un texto específico que indica que hay varias alternativas equivalentes y que el algoritmo continúa con una de ellas.

También se revisan los textos de las hojas.
Las primeras frases están escritas pensando en ejemplos muy pequeños, donde a veces solo llega un dato a cada resultado final.
Al probar conjuntos más variados, esa redacción deja de ser válida.
Se sustituye por una explicación más general, capaz de describir tanto un único ejemplo como varios ejemplos que terminan en la misma clasificación.

Este proceso se repite varias veces durante el desarrollo: al probar nuevos datos aparecen casos que la explicación inicial no cubre bien.
Esos casos se van incorporando al discurso de la aplicación para que el usuario no tenga que interpretar silencios o comportamientos inesperados.


\subsection{Primer panel de selección de datos}

Hasta este momento, los datos usados para entrenar el árbol están fijados dentro del propio proyecto.
Esto es cómodo para las primeras pruebas, porque permite centrarse en el funcionamiento del algoritmo y de la interfaz.
Con el tiempo, esta comodidad empieza a limitar la aplicación: el usuario necesita poder escoger con qué ejemplo trabajar.

El siguiente paso es separar la elección de los datos del entrenamiento.
Primero se prueba un segundo conjunto preparado manualmente, con casos diseñados para forzar ramas más profundas y situaciones menos evidentes.
Esta prueba ayuda a comprobar que el árbol también funciona con ejemplos distintos del primero y que los textos siguen teniendo sentido cuando los datos cambian.

A partir de ahí se crea el panel de selección que se aprecia en la Figura \ref{fig:dtree_dataset_selection_panel}.
Su papel es guiar al usuario antes de empezar el entrenamiento: primero se elige una fuente de datos y después se inicia la construcción del árbol.
La primera opción permite usar el conjunto de ejemplo incluido en la aplicación.
La segunda opción abre la puerta a cargar un archivo CSV.

La carga de archivos se introduce de forma progresiva.
En una primera versión, el panel ya muestra la opción de CSV y todavía está incompleta.
Después se añade la lectura del archivo y la comprobación de que la selección sea válida antes de permitir entrenar.
También se añaden mensajes de éxito o error para que el usuario sepa si puede continuar.

Con este panel, el flujo del modo algorítmico cambia de manera importante.
Antes, el usuario pulsa directamente el botón de comenzar.
Después de esta mejora, primero escoge los datos, luego confirma la selección y finalmente avanza por la construcción del árbol.
Esta separación hace el proceso más comprensible, porque deja claro que el entrenamiento depende de los datos elegidos.

La versión inicial del panel todavía es provisional.
Quedan detalles por ajustar, como mejorar la detección de la respuesta esperada en archivos externos y pulir la transición entre la selección de datos, el árbol y la ventana informativa.
Con esas limitaciones pendientes, el cambio marca un avance importante: el árbol deja de estar ligado a un único ejemplo y empieza a comportarse como una herramienta más flexible.


\subsection{Carga de archivos y navegación por pasos}

El primer ajuste tras introducir el panel de selección es hacer que los archivos CSV puedan usarse realmente para entrenar el árbol.
Hasta ese momento, la carga de datos es una posibilidad visible en la interfaz y todavía necesita más trabajo para integrarse en el flujo completo.
El problema principal está en distinguir qué parte del archivo describe cada ejemplo y qué parte contiene la respuesta que el árbol debe aprender.

Para resolverlo, la aplicación empieza a buscar automáticamente la columna que representa esa respuesta.
La solución se plantea de forma práctica: se reconocen algunos nombres habituales y se separan del resto de características.
Con ello, el usuario puede cargar archivos sencillos sin tener que modificar manualmente la estructura de los datos antes de entrenar.

También se revisa la lectura del archivo para hacerla más fiable.
El objetivo es aceptar tablas simples, con una primera fila de nombres y varias filas de ejemplos, ignorando las líneas vacías.
Esta mejora sigue siendo limitada, ya que está pensada para datos formados por categorías y con una estructura clara.
Con esa base basta para probar el árbol con ejemplos externos al proyecto.

El flujo visual se ajusta a esta nueva forma de empezar.
Al escoger el modo algorítmico, primero aparece el panel para seleccionar los datos.
El árbol y la ventana informativa permanecen ocultos hasta que el usuario hace una selección válida.
Así se evita mostrar una escena vacía o una explicación sin contexto.
Una vez elegidos los datos, la vista pasa directamente al entrenamiento y la ventana indica que el siguiente paso consiste en avanzar por la construcción.

En paralelo empieza a prepararse la navegación hacia atrás.
Hasta ese momento, el entrenamiento solo permite avanzar.
Esta limitación es poco adecuada para una herramienta educativa, porque el usuario puede querer revisar justo el paso anterior para entender por qué aparece una rama o una hoja.

La primera versión de esta navegación hacia atrás solo prepara el camino.
La aplicación empieza a recordar qué pasos ya están ejecutados y cuáles quedan pendientes, de forma que más adelante pueda deshacer una decisión concreta.
Después se añade el botón ``Paso previo'' a la interfaz.
Con él, la construcción del árbol deja de ser estrictamente lineal: el usuario puede avanzar con ``Siguiente paso'' y retroceder cuando necesite revisar el proceso.

Hacer que el retroceso funcione de verdad requiere pensar qué debe ocurrir con cada tipo de elemento del árbol.
Si se deshace una decisión que abre varias ramas, también hay que retirar las partes que dependen de ella.
Si el elemento deshecho es temporal, resulta más claro devolverlo a su estado pendiente que eliminarlo por completo.
Si se vuelve al inicio, el árbol debe quedar vacío y sin conexiones antiguas en pantalla.

Durante las pruebas aparece precisamente ese último problema.
Al regresar al primer paso, algunas conexiones pueden permanecer visibles después de eliminar el árbol.
La corrección consiste en actualizar también las ramas cuando el árbol queda vacío.
Con esto, retroceder hasta el inicio deja la vista en un estado coherente y permite avanzar de nuevo sin arrastrar restos visuales de la ejecución anterior.


\subsection{Primera evaluación visual del árbol}

El último avance de este tramo inicial es una primera versión del modo de evaluación.
Hasta entonces, la aplicación muestra cómo se construye el árbol.
Todavía falta enseñar cómo se usa ese árbol para clasificar ejemplos nuevos.
La evaluación se plantea de forma visual: cada ejemplo de prueba se representa como un objeto que atraviesa el árbol siguiendo las decisiones ya aprendidas.

Para introducir este modo se añaden controles específicos a la interfaz.
Durante el entrenamiento, la evaluación permanece desactivada.
Al terminar la construcción del árbol, el usuario puede pasar a una nueva fase y escoger datos para probar el resultado.
Se reutiliza el panel de selección, ya que su papel sigue siendo el mismo: elegir con qué datos se va a trabajar.

La aplicación empieza entonces a distinguir entre dos momentos.
En el primero, los datos seleccionados sirven para construir el árbol.
En el segundo, los datos seleccionados sirven para comprobar cómo clasifica el árbol ya entrenado.
Esta separación todavía es provisional y permite probar el ciclo completo: entrenar primero y evaluar después.

Para que la evaluación se entienda mejor, cada ejemplo se dibuja como una pieza sencilla que puede moverse por la escena.
